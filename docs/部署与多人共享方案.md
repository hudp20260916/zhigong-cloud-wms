# 部署与多人数据共享方案

> 结论先行：**GitHub Pages 只能托管静态前端，存不了业务数据。**
> 这个系统的数据在服务端 SQLite 里（采购/库存/生产/销售/财务全部走 `/api`），
> 所以「多人共享数据」的关键不是前端放哪，而是**所有人连同一个后端**。
> 下面给出两条已验证可行的路线，按改动量从小到大排序。

---

## 路线 A（推荐）：前端 Pages + 后端云主机

```
GitHub Pages（静态前端，免费）
        │  HTTPS 请求 /api（VITE_API_BASE 指向后端）
        ▼
云端后端（Express + SQLite，所有人共用这一个实例）
```

### 为什么可行

- 本次已完成的改造让这条路**零再开发**：
  - 前端 API 基址支持 `VITE_API_BASE` 环境变量（`web/src/api/client.ts`）；
  - `vite.config.ts` 已设 `base: './'`，产物可放在任何子路径；
  - 后端已开 CORS（`app.use(cors())`），支持跨域前端调用；
  - 路由是 HashRouter，Pages 子路径下刷新不 404；
  - `.github/workflows/deploy-pages.yml` 已就位，push 到 main 自动发布前端。
- 多人共享 = 共享同一个后端实例 + 同一个 `app.db`，天然一致。

### 所需外部服务

| 用途 | 服务 | 说明 |
|---|---|---|
| 前端托管 | GitHub Pages | 免费，本仓库 workflow 自动部署 |
| 后端托管 | Fly.io / Railway（带持久卷）或自有 VPS | **必须挂持久盘**，见下方红字 |
| 域名/HTTPS | 托管平台自带 | Render/Fly/Railway 默认送 HTTPS 域名 |

> ⚠️ **数据持久性红线**：Render/Railway/Fly 的**免费层磁盘是临时的**，
> 实例重启或重新部署后 SQLite 文件会被清空 —— 业务数据全丢。
> 要么上付费持久卷（Railway Volume / Fly Volume，$1~3/月起），
> 要么用一台最便宜的 VPS（腾讯云轻量 2C2G 即可）跑 `node server`，
> 要么加定时备份（见安全注意事项第 5 条）。

### 配置项与环境变量

后端（在托管平台的环境变量面板设置，不要写进仓库）：

| 变量 | 必填 | 说明 |
|---|---|---|
| `JWT_SECRET` | ✅ | 换成 64 位随机串（`openssl rand -hex 32`） |
| `PORT` | – | 平台一般自动注入，默认 3001 |
| `DB_FILE` | 建议 | 指到持久卷路径，如 `/data/app.db` |

前端（仓库 Settings → Secrets and variables → Actions → Variables）：

| 变量 | 必填 | 说明 |
|---|---|---|
| `VITE_API_BASE` | ✅ | 后端完整地址，如 `https://zhigong-api.fly.dev`（末尾不带 `/api`） |

启动命令（monorepo 注意 `-w`）：

```bash
npm ci
npm -w server run start   # 即 tsx src/index.ts
```

### 安全注意事项

1. **`JWT_SECRET` 必须换掉**，默认值 `zhigong-cloud-wms-dev-secret` 只能用于本机开发；泄露等于任何人可伪造登录态。
2. **`.env` 永不入库**（已写进 `.gitignore`），仓库里只有 `.env.example` 模板。
3. **CORS 收紧**：上线后把 `app.use(cors())` 改成 `cors({ origin: 'https://你的pages域名' })`，避免任意网站都能调你的接口。
4. **HTTPS 强制**：Pages 是 HTTPS，后端也必须 HTTPS（平台自带），否则 token 会被中间人截获。
5. **SQLite 备份**：SQLite 是单文件，每日 `cp app.db backup-$(date +%F).db` 或用平台卷快照；也可以加一个 cron 调 `/api` 之外的自定义导出。
6. **演示账号**：部署前把 7 个演示账号密码全部改掉，或直接删除 seed 数据里的默认账号。
7. **打印数据接口带 token 参数**（`renderUrl`）仅便于新窗口打开，若担心日志泄漏可改用 cookie 方案，当前内部使用可接受。

## 路线 B：迁移到 BaaS（真·无服务器）

把 `server/src` 的数据访问层整体替换为 Supabase / 腾讯云开发（CloudBase）/ Firebase：

- SQLite → 托管 Postgres（Supabase）或文档数据库（CloudBase）；
- 自研 JWT 鉴权 → BaaS Auth + 行级安全（RLS）；
- 打印渲染、BOM 展开、库存台账等逻辑迁到 BaaS Edge Functions。

**代价**：`server/src/modules` 下 11 个模块全部重写，库存台账（`core/ledger.ts`）三条硬约束要在 RLS 里重新实现一遍，预计是一个独立的大版本，不建议为了「部署」顺手做。适合的时机是：团队人数超过 SQLite 并发写上限（约 10 人同时高频写入）或需要手机端离线时。

## 部署操作清单（路线 A，按顺序执行）

### 第 1 步：本地建仓提交

```bash
cd C:\Users\admin\Documents\生产管理系统
git init
git add .
git commit -m "v1.4.6: P6 + 移动端适配 + 模板编辑页重构"
```

### 第 2 步：建 GitHub 仓库并推送

网页方式（无 gh CLI 时）：

1. GitHub → New repository → 起名（如 `zhigong-cloud-wms`）→ **不要**勾选 README/.gitignore 初始化
2. 复制仓库地址，执行：

```bash
git remote add origin https://github.com/<你的用户名>/zhigong-cloud-wms.git
git branch -M main
git push -u origin main
# 推送时弹窗要求登录：用「Personal Access Token」当密码（Settings → Developer settings → Tokens → 生成，勾选 repo 权限）
```

### 第 3 步：部署后端（以 Fly.io 为例，Railway 同理）

```bash
# 本机装 flyctl 后：
fly launch --no-deploy          # 选区域、确认不加数据库
fly volumes create zhigong_data --size 1   # 1GB 持久卷，SQLite 放这里
# fly.toml 里确认 mount 挂到 /data
fly secrets set JWT_SECRET=$(openssl rand -hex 32)
fly deploy
```

环境变量最终形态：`DB_FILE=/data/app.db`、`JWT_SECRET=<随机串>`、`PORT=8080`（平台覆盖）。
部署完打开 `https://<app>.fly.dev/api/health` 应返回 `{"ok":true,...}`。

### 第 4 步：配置前端部署

1. 仓库 Settings → Secrets and variables → Actions → **Variables** 标签 →
   新建 `VITE_API_BASE` = 后端地址（如 `https://zhigong-api.fly.dev`）
2. Settings → Pages → Source 选 **GitHub Actions**
3. push 任意提交（或手动 Run workflow），等 Actions 跑完，得到
   `https://<用户名>.github.io/zhigong-cloud-wms/`

### 第 5 步：验收（照着点一遍）

| 检查项 | 预期 |
|---|---|
| 打开 Pages 地址 | 显示登录页 |
| admin 登录 | 进工作台，指标有数 |
| 手机同 Wi-Fi 打开 Pages 地址 | 单列布局、无横向滚动 |
| 两台设备同时建一张采购入库单 | 库存都实时变化（共享同一后端） |
| 打印采购订单 | 合计行与表头对齐（本次修复项） |
| viewer 登录 | 看不到金额字段 |

### 第 6 步（可选）：收紧安全

- `app.use(cors())` → `cors({ origin: 'https://<用户名>.github.io' })`
- 改掉所有演示账号密码
- 给持久卷配每日快照
